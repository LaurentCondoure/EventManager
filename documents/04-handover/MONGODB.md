## What is MongoDB

MongoDB is a **document-oriented** database. Instead of storing rows in tables, it stores **documents** (JSON-like objects called BSON) in **collections**.

Example:
```json
{
  "_id": ObjectId("661f1a2b3c4d5e6f7a8b9c0d"),
  "EventId": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "UserName": "Thomas",
  "Text": "Super concert !",
  "Rating": 4,
  "CreatedAt": "2026-04-26T14:30:00Z"
}
```

## Why MongoDB for comments

Comments are **semi-structured data** — the text field is optional, the content is variable length, and the structure may evolve (likes, nested replies, media). MongoDB allows adding fields to some documents without migrating the entire collection.

| Concern | SQL Server | MongoDB |
|---------|-----------|---------|
| Schema | Fixed, migration required | Flexible, per-document |
| Relations | Foreign keys, joins | Denormalized (eventId as reference) |
| Transactions | ACID | Not required here |
| Free text | Possible | Natural fit |

## Key concepts

### Collection vs Table

A **collection** is the MongoDB equivalent of a table, but without a fixed schema. Two documents in the same collection can have different fields.

### Document vs Row

A **document** is a BSON object (Binary JSON). Each document has a unique `_id` field — by default an `ObjectId`, a 12-byte identifier generated by the driver.

### ObjectId

By default, if `_id` is left unset, the driver generates an `ObjectId` client-side and populates it before sending the insert — no round-trip to the database is needed to know the id.

That automatic generation relies on the property being the driver's native `ObjectId` type (or configured with an `IdGenerator`). In this codebase, `EventComment.Id` is a `string`, so `MongoDbCommentRepository.CreateAsync` generates it explicitly instead of relying on the driver default:

```csharp
// EventManager.Infrastructure/Repositories/MongoDbCommentRepository.cs
public async Task<string> CreateAsync(EventComment comment)
{
    comment.Id = ObjectId.GenerateNewId().ToString();
    await _collection.InsertOneAsync(comment);
    return comment.Id; // already known before the insert — generated by the application, not the driver
}
```

## Working with MongoDB in .NET

The NuGet package used is `MongoDB.Driver`.

### Connection and collection

```csharp
public class MongoDbCommentRepository(IMongoClient client, IOptions<MongoDbOptions> options) : ICommentRepository
{
    private readonly IMongoCollection<EventComment> _collection =
        client.GetDatabase(options.Value.DatabaseName).GetCollection<EventComment>("event_comments");
}
```

- `GetDatabase()` never returns null — it is safe to chain directly with `GetCollection()`
- `IMongoCollection<T>` is a client-side handle — no data is loaded at construction time

### Configuration (IOptions pattern)

```json
// appsettings.json
{
  "MongoDb": {
    "ConnectionString": "mongodb://localhost:27017",
    "DatabaseName": "EventsDB"
  }
}
```

Non-sensitive values (`DatabaseName`) go in `appsettings.json`. Credentials, if any, go in User Secrets.

### Reading — Filter and Sort

```csharp
var filter = Builders<EventComment>.Filter.Eq(c => c.EventId, eventId);
// translated by the driver into: { EventId: <eventId> }
var sort   = Builders<EventComment>.Sort.Descending(c => c.CreatedAt);
// translated by the driver into: { CreatedAt: -1 }

return await _collection.Find(filter).Sort(sort).ToListAsync();
// Equivalent to: db.event_comments.find({ EventId: eventId }).sort({ CreatedAt: -1 })
```


`Builders<EventComment>.Filter` and `.Sort` are entry points into `FilterDefinitionBuilder<T>` and `SortDefinitionBuilder<T>`. Calling `Eq()` or `Descending()` does not run any query — it builds a `FilterDefinition<T>` / `SortDefinition<T>` object. Nothing is sent to MongoDB yet.

The lambda (`c => c.EventId`) is never executed as C# code. It is captured as an **expression tree**, which the driver walks to resolve the corresponding BSON field name — by default, the exact member name (`EventId`, not `eventId`), unless a `[BsonElement]` attribute or a naming convention overrides it.

Only `.Find(filter).Sort(sort).ToListAsync()` actually sends the resulting BSON query document to the server.

In practice,  `c => c.EventId` is checked by the C# compiler. If the property is renamed, the build will fail. A raw query (`new BsonDocument("EventId", eventId)`) would instead fail silently at runtime if the field name were wrong or renamed.

### Writing

MongoDB has no equivalent of a SQL `DEFAULT GETUTCDATE()` — there is no server-side mechanism setting `CreatedAt`. If it isn't assigned before `InsertOneAsync`, the document is written with the CLR default (`DateTime.MinValue`), not the actual insert time. This is why the timestamp is set by the caller, not by the repository:

```csharp
// EventManager.Domain/Services/EventService.cs — CreatedAt is set here, before the repository is even called
var comment = new EventComment
{
    EventId   = eventId,
    UserId    = input.UserId,
    UserName  = input.UserName,
    Text      = input.Text,
    Rating    = input.Rating,
    CreatedAt = DateTime.UtcNow
};

var id = await commentRepository.CreateAsync(comment);
```

```csharp
// EventManager.Infrastructure/Repositories/MongoDbCommentRepository.cs — CreateAsync only handles persistence
comment.Id = ObjectId.GenerateNewId().ToString();
await _collection.InsertOneAsync(comment);
// Equivalent to: db.event_comments.insertOne({ _id: ObjectId("..."), EventId: ..., UserId: ..., UserName: ..., Text: ..., Rating: ..., CreatedAt: ... })
```

*N.B :* The repository is a pure persistence boundary — it does not decide *when* a comment was created, only how it gets stored. That decision belongs to `EventService`, the caller.

## Dependency injection

```csharp
// Program.cs
builder.Services.Configure<MongoDbOptions>(
    builder.Configuration.GetSection(MongoDbOptions.SectionName));

builder.Services.AddSingleton<IMongoClient>(sp =>
    new MongoClient(sp.GetRequiredService<IOptions<MongoDbOptions>>().Value.ConnectionString));

builder.Services.AddScoped<ICommentRepository, MongoDbCommentRepository>();
```

`IMongoClient` is registered as **Singleton** — the driver manages an internal connection pool and is designed to be shared across the application lifetime.

## Unit testing

### Mocking Find()

**Problem:** `Find()` on `IMongoCollection<T>` is also an extension method — Moq raises `NotSupportedException` when trying to set it up, regardless of the filter syntax used (`lambda` or `Builders<T>.Filter`). The filter type is irrelevant; the issue is the method itself.

```csharp
// Both fail — Find() is an extension method
_collectionMock.Setup(c => c.Find(x => x.EventId == id, null));                          // ❌
_collectionMock.Setup(c => c.Find(Builders<EventComment>.Filter.Eq(...), null));          // ❌
```

**Available solutions:**

| Solution | Type | Trade-off |
|---|---|---|
| Mock `FindAsync()` | Unit test | `FindAsync()` is on the interface — no external dependency |
| Testcontainers / EphemeralMongo | Integration test | Real MongoDB, slower, requires Docker or binary |
| Custom abstraction interface | Unit test | Isolates the driver completely, adds indirection |

**Chosen solution:** Mock `FindAsync()` directly — it is declared on `IMongoCollection<T>` and returns `IAsyncCursor<T>`, which we already know how to mock (see below).

---

### Mocking ToListAsync()

`ToListAsync()` is a **static extension method** on `IAsyncCursorSourceExtensions` — not a member of `IFindFluent<T,T>`. Moq can only mock interface members and virtual methods. An extension method is syntactic sugar for a static call, so it is **invisible to Moq**.

```csharp
// Cannot mock — static extension method, not on the interface
findFluent.Setup(f => f.ToListAsync(...)); // ❌
```

Internally, `ToListAsync()` calls `ToCursorAsync()`, which **is** declared on the interface:

```csharp
// IAsyncCursorSource<T> — mockable
Task<IAsyncCursor<TDocument>> ToCursorAsync(CancellationToken cancellationToken = default);
```

By mocking `ToCursorAsync()` to return a controlled `IAsyncCursor<T>`, you intercept the actual execution path that `ToListAsync()` follows — without needing to mock the extension method itself.

```csharp
var cursorMock = new Mock<IAsyncCursor<EventComment>>();
cursorMock.Setup(c => c.Current).Returns(comments);
cursorMock
    .SetupSequence(c => c.MoveNextAsync(It.IsAny<CancellationToken>()))
    .ReturnsAsync(true)   // first batch
    .ReturnsAsync(false); // end of cursor

var findFluent = new Mock<IFindFluent<EventComment, EventComment>>();
findFluent
    .Setup(f => f.Sort(It.IsAny<SortDefinition<EventComment>>()))
    .Returns(findFluent.Object);
findFluent
    .Setup(f => f.ToCursorAsync(It.IsAny<CancellationToken>()))
    .ReturnsAsync(cursorMock.Object); // ✅ intercepted here
```

### Mocking InsertOneAsync()

`InsertOneAsync()` is on the interface and can be mocked directly. Use a Moq `Callback` to simulate the driver populating `comment.Id` after insert:

```csharp
_collectionMock
    .Setup(c => c.InsertOneAsync(
        It.IsAny<EventComment>(),
        It.IsAny<InsertOneOptions>(),
        It.IsAny<CancellationToken>()))
    .Callback<EventComment, InsertOneOptions, CancellationToken>(
        (comment, _, _) => comment.Id = "507f1f77bcf86cd799439011")
    .Returns(Task.CompletedTask);
```

## GuidRepresentation in MongoDB Driver 3.x

### Problem

MongoDB Driver 3.x raises the following exception when inserting or querying a document that contains a `Guid` property without explicit serialization configuration:

```
BsonSerializationException: GuidSerializer cannot serialize a Guid when GuidRepresentation is Unspecified.
```

### Explanation

Prior to version 3.x, the MongoDB .NET driver inferred the GUID representation automatically (defaulting to `CSharpLegacy`). In driver 3.x this inference was removed: the driver refuses to serialize a `Guid` until the application explicitly declares which binary encoding to use.

Our `EventComment` entity holds two `Guid` properties — `EventId` and `UserId` — both of which trigger this error without configuration.

The available GUID representations are:

| Value | Description |
|---|---|
| `CSharpLegacy` | Old .NET driver default (subtype 3) |
| `JavaLegacy` | Java driver legacy |
| `PythonLegacy` | Python driver legacy |
| `Standard` | RFC 4122 UUID (subtype 4) — recommended for new projects |
| `Unspecified` | Driver 3.x default — raises an exception on use |

`Standard` was chosen: it is the RFC-compliant encoding, interoperable with other ecosystems, and correct for a new application.

### Options considered

| Option | Approach | Decision |
|---|---|---|
| **A — Fixture-level** | Configure `BsonDefaults.GuidRepresentation = GuidRepresentation.Standard` in the test fixture only | Rejected — fixes tests but not the production API; deferred problem |
| **B — Global** | Set the default at application startup before any driver call | Rejected — affects all collections globally; risks breaking future types with different requirements |
| **B+ — BsonClassMap** | Register a targeted `BsonClassMap<EventComment>` in Infrastructure, configure only the two affected properties | **Chosen** — surgical, Infrastructure-scoped, no Domain dependency |
| **C — Attribute** | Add `[BsonGuidRepresentation(GuidRepresentation.Standard)]` directly on the entity properties | Rejected — adds `MongoDB.Bson` dependency to the Domain layer, violating Clean Architecture |

### Chosen resolution — Option B+

A static helper class `MongoDbMappings` in `EventManager.Infrastructure` registers a `BsonClassMap` for `EventComment`. Only the two `Guid` properties are configured; everything else is auto-mapped.

**`backend/EventManager.Infrastructure/Mappings/MongoDbMappings.cs`**

```csharp
using EventManager.Domain.Entities;
using MongoDB.Bson;
using MongoDB.Bson.Serialization;
using MongoDB.Bson.Serialization.Serializers;

public static class MongoDbMappings
{
    private static readonly object _lock = new();
    private static bool _registered;

    public static void Register()
    {
        if (_registered) return;

        lock (_lock)
        {
            if (_registered) return;

            BsonClassMap.RegisterClassMap<EventComment>(map =>
            {
                map.AutoMap();
                map.MapMember(c => c.EventId).SetSerializer(new GuidSerializer(GuidRepresentation.Standard));
                map.MapMember(c => c.UserId).SetSerializer(new GuidSerializer(GuidRepresentation.Standard));
            });

            _registered = true;
        }
    }
}
```

**Why double-checked locking?**

xUnit v3 runs test classes in parallel. When integration tests boot multiple `WebApplicationFactory` instances simultaneously, each triggers `Program.cs → MongoDbMappings.Register()` in the same AppDomain. Without the lock, two threads can both read `_registered = false` before either has finished writing, and `BsonClassMap.RegisterClassMap` throws `ArgumentException: An item with the same key has already been added`. The double-checked locking pattern eliminates this race condition without locking on every call after initialization.

**Registration points**

**Important : ** `MongoDbMappings.Register()` must be called before any MongoDB driver operation:

```csharp
// Program.cs — before WebApplicationBuilder
MongoDbMappings.Register();
WebApplicationBuilder builder = WebApplication.CreateBuilder(args);
```

```csharp
// MongoDbFixture.cs — before starting the container
public async ValueTask InitializeAsync()
{
    MongoDbMappings.Register();
    await _container.StartAsync();
    Client = new MongoClient(_container.GetConnectionString());
}
```
